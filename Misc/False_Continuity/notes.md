# False Continuity (Misc, 804) — 分析筆記

## 檔案

`False_Continuity.zip` → **144 張 512×512 PNG**，檔名為隨機 64-bit hex（無順序資訊）。
每張是一張「紙屑」照片：米白紙張、印著等寬字體的亂碼文字、背景有極淡的星圖／羅盤浮水印。
144 張全部 pixel-unique，PNG 無任何 metadata chunk。

**不是拼圖**（不是把 144 張拼成一張大圖）。

## 🎯 核心機制：灰字 vs 黑字

每張紙屑上，**少數字元是用淺灰色印的**，其餘是純黑。這就是題名 False Continuity 的意思：
看得見的連續文字是誘餌，**灰字才是 payload**。

分界非常乾淨，用 connected component 的墨色分布可以完全分開：

| 類別 | 最暗像素 `mn` | 墨色 10th percentile | 數量 |
|---|---|---|---|
| 正常黑字（誘餌） | 0 ~ 20 | 6 ~ 16 | ~4390 |
| **灰字（payload）** | 45 ~ 98 | 58 ~ 98 | **764** |

（40~44 之間幾乎沒有東西，門檻設 45 即可。
 注意 >100 的約 20 個是浮水印雜訊，浮水印本身在 191~210，比灰字更淡。）

## 已建立的 pipeline（都在 scratchpad，未污染題目資料夾）

1. **去斜**：紙屑在 **360° 全範圍**隨機旋轉。用 glyph 中心的投影直方圖在 ±90° 搜尋最佳角度，
   再用「基線 std 比頂線 std 小」的統計解 180° 正反歧義（Latin 文字底部對齊、頂部不齊）。
2. **切字**：per-glyph 自適應門檻（該字最暗值與紙色的中點）重新取 bbox，
   避免灰字被 anti-alias halo 撐大。
3. **切行**：依 y 中心分群，間距門檻 = 字高中位數 × 0.6。
   結果 **5151 個 glyph**，主要行長 10–11 字（短行是撕裂邊緣）。
4. **OCR**：本機無 tesseract/easyocr，改用 **DejaVu Sans Mono 自建 template matcher**。
   特徵 = 形狀距離 + 長寬比 + 基線上下緣 + 字高，權重用已知正解網格搜尋調出
   （0.05 / 0.05 / 0.1，template 32px，另按每張紙屑字距校正縮放）。
   **單字準確率 19/20 = 95%**。

驗證用的已知正解（肉眼判讀那張 `0391773af82be9ef`）：
```
*T80,a9jJB      ← 8 是灰的
/K9smNPzg3      ← / 和 9 是灰的
.hkm0Ih_<H      ← 0 是灰的
```

## 重要發現：144 張 = 72 組「重複對」

用 4-gram / 5-gram 比對，發現紙屑是**成對出現的**：同一張紙屑被拍了兩次。
目前用貪婪配對已配出 **42 對**（84 張），其餘 60 張是字數太少的小碎片，訊號不足。

驗證範例（`0391773af82be9ef` vs `334fb64834bd241e`）：

```
+T[8]O,a9jJB          +T[8]O,a9jJB
[/]K[9]smNPzg3        [/]K[9]smNPzg3
hkm[D][I]h<H          hkm[D][T]h<H     ← 只有這裡不同，且是 OCR 誤判不是真差異
_                     _
[q]^ou__b[_]:'        [q]^ou__b[_]:'
```

→ **重複對的灰字位置完全相同**，所以重複**不是**用來編碼資料的，
   而是給**錯誤更正**用的（兩張投票可以修掉 OCR 誤判）。

所以實際 payload 約 **382 個唯一灰字元**。

## 目前卡點：排序

還不知道 72 組紙屑的正確順序。已排除：

- ❌ 檔名（隨機 64-bit hex，無結構）
- ❌ 誘餌文字接龍（文字是亂碼，跨紙屑沒有可接續的重疊，除了上述「重複對」）
- ❌ 灰字墨色深淺編碼順序（45–98 連續分布，像是渲染雜訊而非資料通道）
- ❌ 背景浮水印（星圖／羅盤在 191–210，是裝飾性紙張材質）

## 下一步

1. 用「重複對」投票修正 OCR，把 382 個唯一灰字元的準確率再拉高
2. 找排序線索：紙張**撕裂邊緣的形狀**是否能兩兩接合（真正的 jigsaw，但是接邊不是拼圖）
3. 或：灰字在紙屑內的**相對位置**（行號、列號）是否本身就是索引
4. 或：先假設 382 字元是 base64／base85，用頻率分析反推正確字元集與排序
