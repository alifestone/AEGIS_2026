# False Continuity (Misc, 804) — 分析筆記

## 檔案

`False_Continuity.zip` → **144 張 512×512 PNG**，檔名為隨機 64-bit hex（無順序資訊）。
每張是一張「紙屑」照片：米白紙張、印著等寬字體的亂碼文字、背景有極淡的星圖／羅盤浮水印。
144 張全部 pixel-unique，PNG 無任何 metadata chunk。

**不是拼圖**（不是把 144 張拼成一張大圖）。

## 🎯 核心機制：灰字 vs 黑字

每張紙屑上，**少數字元是用淺灰色印的**，其餘是純黑。這就是題名 False Continuity 的意思：
看得見的連續文字是誘餌，**灰字才是 payload**。

分界非常乾淨，用 connected component 的墨色分布可以完全分開：

| 類別 | 最暗像素 `mn` | 墨色 10th percentile | 數量 |
|---|---|---|---|
| 正常黑字（誘餌） | 0 ~ 20 | 6 ~ 16 | ~4390 |
| **灰字（payload）** | 45 ~ 98 | 58 ~ 98 | **764** |

（40~44 之間幾乎沒有東西，門檻設 45 即可。
 注意 >100 的約 20 個是浮水印雜訊，浮水印本身在 191~210，比灰字更淡。）

## 已建立的 pipeline（都在 scratchpad，未污染題目資料夾）

1. **去斜**：紙屑在 **360° 全範圍**隨機旋轉。用 glyph 中心的投影直方圖在 ±90° 搜尋最佳角度，
   再用「基線 std 比頂線 std 小」的統計解 180° 正反歧義（Latin 文字底部對齊、頂部不齊）。
2. **切字**：per-glyph 自適應門檻（該字最暗值與紙色的中點）重新取 bbox，
   避免灰字被 anti-alias halo 撐大。
3. **切行**：依 y 中心分群，間距門檻 = 字高中位數 × 0.6。
   結果 **5151 個 glyph**，主要行長 10–11 字（短行是撕裂邊緣）。
4. **OCR**：本機無 tesseract/easyocr，改用 **DejaVu Sans Mono 自建 template matcher**。
   特徵 = 形狀距離 + 長寬比 + 基線上下緣 + 字高，權重用已知正解網格搜尋調出
   （0.05 / 0.05 / 0.1，template 32px，另按每張紙屑字距校正縮放）。
   **單字準確率 19/20 = 95%**。

驗證用的已知正解（肉眼判讀那張 `0391773af82be9ef`）：
```
*T80,a9jJB      ← 8 是灰的
/K9smNPzg3      ← / 和 9 是灰的
.hkm0Ih_<H      ← 0 是灰的
```

## ⚠️ 已更正：不是 72 組重複對，是 45~46 對 + 52~54 張真單張

> **2026-09-18 更正**：planner 原本寫「144 張 = 72 組重複對」，**這是錯的**。
> 由 misc session 指出，planner 已獨立驗證確認。錯誤的推論與修正如下。

### 正確的結構

用「行數 + 每行長度輪廓 + 逐位置 char 一致率」做結構比對（不靠 OCR 文字模糊比對）：

| 類別 | 數量 | 最佳配對一致率 |
|---|---|---|
| 真重複對 | **45~46 對**（90~92 張） | **0.974 ~ 0.981** |
| **真單張** | **52~54 張** | **最高只有 0.031** |

**兩者之間沒有灰色地帶**：真對是 0.97 以上，單張最高 0.03，中間完全空白。
所以那 52~54 張是**真的沒有對象可配**，不是配對演算法不夠好。

### planner 原本錯在哪（避免重蹈）

1. ❌ 原本用 4-gram/5-gram 交集做貪婪配對，把 144 張硬湊成對，得出「72 組」
   → n-gram 交集在亂碼文字上會有隨機重疊，門檻沒拉開就會硬配出假對
2. ❌ 原本宣稱「配不出來的 60 張是碎片太小、訊號不足」——**這句話是錯的，而且方向相反**：
   - 單張組：平均 **37.0** glyph、中位數 40、最大 57
   - 有對組：平均 **35.0** glyph、中位數 31、最大 58
   - 單張組裡有 12 張是 52~57 glyph 的大張
   → **單張反而比有對的更大**。照原本的說法去「補配對」是浪費時間（misc 已實測踩過）

### 對 payload 規模的影響

- 不重複的紙屑數 = 45 + 54 = **約 98~99 張**（不是 72）
- 唯一 payload 灰字數 = **約 536 ~ 544 個**（不是 382）

536 / 544 這個量級比 382 合理得多：
若是 base64，536 字元 ≈ 402 bytes，比較像藏了一段結構化資料。

### 仍然成立的部分

- 45/46 對之中，**灰字 mask 完全相同**（唯一一對不同是 OCR 誤判：bb7ed980 / d1f490ac）
  → **重複確實是給錯誤更正用的，不是編碼通道**。這個結論不變。

## 原始紀錄（含上述已更正的錯誤，保留供對照）

### 144 張 = 72 組「重複對」← 此標題下的數字已被更正

用 4-gram / 5-gram 比對，發現紙屑是**成對出現的**：同一張紙屑被拍了兩次。
目前用貪婪配對已配出 **42 對**（84 張），其餘 60 張是字數太少的小碎片，訊號不足。

驗證範例（`0391773af82be9ef` vs `334fb64834bd241e`）：

```
+T[8]O,a9jJB          +T[8]O,a9jJB
[/]K[9]smNPzg3        [/]K[9]smNPzg3
hkm[D][I]h<H          hkm[D][T]h<H     ← 只有這裡不同，且是 OCR 誤判不是真差異
_                     _
[q]^ou__b[_]:'        [q]^ou__b[_]:'
```

→ **重複對的灰字位置完全相同**，所以重複**不是**用來編碼資料的，
   而是給**錯誤更正**用的（兩張投票可以修掉 OCR 誤判）。

所以實際 payload 約 **382 個唯一灰字元**。

## 目前卡點：排序

還不知道 72 組紙屑的正確順序。已排除：

- ❌ 檔名（隨機 64-bit hex，無結構）
- ❌ 誘餌文字接龍（文字是亂碼，跨紙屑沒有可接續的重疊，除了上述「重複對」）
- ❌ 灰字墨色深淺編碼順序（45–98 連續分布，像是渲染雜訊而非資料通道）
- ❌ 背景浮水印（星圖／羅盤在 191–210，是裝飾性紙張材質）

## 下一步

## pwn_agent 的獨立佐證：差異字元的 base64 命中率有統計顯著性

（2026-09-18，pwn_agent 短暫支援期間。使用者已指示全員轉 Pwn，此處僅留紀錄。）

我從**位元/字元集**角度切入（沒看到 planner 的 `8c77011` 之前），
結論與 planner「紙屑上是一份 base64 文件」的突破**獨立吻合**。

用**方向修正後**的 48 個差異字元（`fc_ocr2.pkl` 版本）：

```
A: IOr7GaurL=rod1SJ5Dwr1cc7JPoMwPBPesYQso6DszBBzSoT
B: TI[vcH3o3=gH5MwT8snGho>sccazHxlXr/BmoJAdvxZvxgxc
```

| 集合 | 落在 base64 字母表的比率 |
|---|---|
| **A（48 字元）** | **1.000（48/48，完全命中）** |
| **B（48 字元）** | 0.958（46/48） |
| A+B 合計 | 0.979（94/96） |
| 對照：全體灰字（status.md 修正 4） | 0.74 |
| 對照：ASCII 33~126 均勻分布的期望值 | 0.691 |

二項檢定（H0：字元均勻取自 ASCII 33–126，p=0.691）：
**觀察 94/96 命中，p-value = 4.0e-13** → 極顯著，**不是巧合**。

**B 的兩個例外正好都是典型 OCR 混淆**：
- `[` @ idx 2 → 很可能是 `l` / `I` / `1`
- `>` @ idx 22 → 很可能是 `7` / `?`

修掉這兩個後 B 也會 100% 落在 base64 字母表內。

→ 這從第三個角度（字元集統計）支持「底層資料是 base64」，
  與 planner 目視確認的 `dmVsb3BlIH...` = `"velope"` 互相獨立佐證。

### 已排除（避免後人重做）

- ❌ **index 9 的 `=` 不是統計訊號**：A/B 在 index 9 是唯一相同的位置，
  但依實際字元分布計算，48 個位置中出現相同位置的**期望值恰好是 1.00**，
  觀察到 1 個完全在預期內。（`=` 在兩串各只出現 1 次又同位置是 1/48 ≈ 2% 的巧合，
  不足以單獨支撐推論。）
- ❌ **把 48 個差異字元直接當 base64 解**：試過 as-is / 去掉 `=` /
  在 index 9 處旋轉 / A·B 交錯 / 修復 `[`·`>` 的 7×7 候選組合，
  全部 0 命中（printable 比率門檻 0.9）。
  → 與 crypto/planner 的結論一致：**順序才是關鍵，不是編碼本身**。
